# 09_DATA_MODEL.md

## Status

Version: 0.1  
Document type: Engineering specification  
Owner: Human project team  
Depends on: `08_SYSTEM_ARCHITECTURE.md`  
Purpose: Define the minimum persistent data model required for traceability, workflow control, rendering, and future auditing.

---

## 1. Data Model Principles

The database is the operational source of truth.

The data model must support:

- provenance;
- workflow state;
- human decisions;
- provider usage;
- deterministic rendering;
- correction/debugging;
- future migration from SQLite to PostgreSQL.

Do not store important project state only in prompts, chat transcripts, logs, or generated prose.

---

## 2. Identifier Strategy

Primary entity IDs should use UUIDs generated by the application.

Human-facing short IDs may be derived or separately stored for display.

Examples:

- `TOP-...`
- `SRC-...`
- `CLM-...`
- `PST-...`
- `AST-...`

The database must not depend on sequential public IDs.

---

## 3. Time Rules

Store timestamps in UTC.

User interfaces may display Asia/Kolkata time.

At minimum use:

- `created_at`;
- `updated_at`;

where relevant.

External source timestamps should be stored separately from internal creation timestamps.

## 5. DiscoveryRun

Represents one scheduled or manually-triggered discovery scan.

Fields:

- `id`
- `trigger_type` — `SCHEDULED` / `MANUAL`
- `started_at`
- `completed_at`
- `status`
- `requested_candidate_count`
- `trending_target_count`
- `undercovered_target_count`
- `provider_metadata_json`
- `error_summary`

Purpose:

- prevent duplicate runs;
- trace how a topic entered the system;
- measure discovery quality and cost.

## 10. Claim

Represents one atomic factual proposition.

Fields:

- `id`
- `human_id`
- `topic_id`
- `research_packet_id`
- `claim_text`
- `claim_type`
- `verification_status`
- `risk_level`
- `confidence`
- `entity_data_json`
- `structured_value_json`
- `period_start`
- `period_end`
- `as_of_at`
- `is_derived`
- `derivation_json`
- `requires_human_review`
- `notes`
- `created_at`
- `updated_at`

### `structured_value_json`

May contain:

```json
{
  "value": 18.0,
  "unit": "percent",
  "display": "18%"
}
```

or:

```json
{
  "value": 146145,
  "unit": "km",
  "display": "1.46 lakh km"
}
```

The `display` value should be created by deterministic formatting logic after verification.

---

## 11. Derived Claims

A derived claim must preserve:

- input claim IDs;
- operation/formula identifier;
- exact computation inputs;
- output value;
- code version or derivation version where practical.

Example:

```json
{
  "formula": "percentage_change",
  "inputs": ["CLM-A", "CLM-B"],
  "result": 25.0
}
```

An LLM must not be the authoritative calculator.

## 13. Verification

Represents one verification pass on one claim.

Fields:

- `id`
- `claim_id`
- `model_run_id`
- `verifier_type` — `MODEL` / `HUMAN`
- `verdict`
- `confidence`
- `rationale_summary`
- `missing_evidence_json`
- `review_required`
- `created_at`

Do not store private chain-of-thought.

Store only concise reviewable rationale.

A claim may have multiple verification records.

The `Claim.verification_status` is the current accepted state.

## 16. Post-to-Claim Relationship

The implementation should support explicit mapping between post content and claims.

A normalized table such as `post_claims` or `slide_claims` is preferred over relying only on JSON.

Minimum fields:

- `post_id` or `slide_id`
- `claim_id`
- `usage_role`

This enables QA to ask:

> Which verified claim supports this displayed number or sentence?

## 23. Risk Level

Initial risk levels:

- `LOW`
- `MEDIUM`
- `HIGH`
- `CRITICAL`

`CRITICAL` should be reserved for cases where the system should stop and require explicit human handling.

Risk is not the same as claim confidence.

---

## 24. Soft Delete / Archival

Do not hard-delete important editorial provenance through normal UI actions.

Topics, posts, and research items should generally be archived or rejected rather than physically deleted.

Caches and temporary model artifacts may follow retention rules later.

---

## 25. Corrections

Version 1 should reserve a path for correction records, even if the full correction workflow is implemented later.

A correction should be able to reference:

- original post;
- affected claim;
- discovered error;
- corrected claim;
- human decision;
- corrective action.

---

## 26. Database Constraints

At minimum enforce:

- foreign keys;
- unique source canonical URL where appropriate;
- unique `(post_id, slide_index)`;
- non-null critical timestamps;
- valid enum values through application + migration constraints where practical;
- no approval without a valid target entity;
- no verification without a valid claim.

Database constraints supplement application validation.

---

## 27. Transaction Rules

State transition + audit event should normally commit atomically.

Examples:

- approve post + create approval record + update post state;
- accept verification + update claim status + append audit event.

Avoid partial state where the entity changed but provenance did not.

---

## 28. Pydantic vs ORM

SQLAlchemy ORM models define persistence.

Pydantic schemas define validated service and provider boundaries.

Do not expose mutable ORM entities directly to model-provider code.

Convert to explicit request/response schemas.

---

## 29. Sensitive Data

Version 1 should minimize personal data.

Store only what is required to distinguish the two human reviewers, such as configured aliases or Telegram user IDs.

Do not collect audience demographic profiles.

Do not store voter or political-targeting profiles.

---

## 30. Golden Rule

**If a future reviewer asks “where did this number, sentence, image, decision, or cost come from?”, the data model should make the answer recoverable.**
